01

Токен бота утекает в parser.log через traceback

logging_setup.py:41 проверено запуском

RedactTokenFilter правит только record.msg. Текст исключения форматтер дописывает отдельно из record.exc_info, минуя фильтр. Собственный прогон:

direct: https://api.telegram.org/bot***TOKEN***/sendMessage        ← замаскировано
ConnectionError: HTTPSConnectionPool url=/bot123456:AAFAKE_TOKEN.../  ← НЕ замаскировано

Достижимо из любого log.exception с цепочкой к api.telegram.org: runtime.py, app.py, bot.py, __main__.py. AGENTS.md прямо требует обратного.

ИсправлениеПеренести маскировку с логгера на хендлеры и переопределить Formatter.format, прогоняя итоговую строку (вместе с traceback) через redact_token.
02

Поток может уснуть на 6 часов внутри одного запроса

net.py:41 проверено запуском

respect_retry_after_header=True без потолка. В установленном urllib3 2.7.0:

DEFAULT_RETRY_AFTER_MAX = 21600   # 6 часов
RETRY_AFTER_STATUS_CODES = {413, 429, 503}

urllib3 делает time.sleep(retry_after) напрямую — ни timeout=, ни STOP_EVENT это не прерывают. Один 429 Retry-After: 21600 — и parser/bot/twitch-worker висит часами без единой строки в логе. Даже без экстремального заголовка: 5 попыток × 15с + backoff ≈ 74с вместо заявленных 15 — из-за этого app.py join(timeout=REQUEST_TIMEOUT+5) истекает при сбое, и save_seen() пропускается.

ИсправлениеRetry(..., retry_after_max=30, backoff_max=10); пересчитать бюджет join от реального потолка, а не от REQUEST_TIMEOUT.
03

/active может сам сорвать стоп-гвард в fail-open

betboom.py:471 проверено чтением кода

classify_wheels кормит _apply_stub_guard без возможности отказаться. Но /active — массовый обход всех колёс за сутки (окно ACTIVE_MAX_AGE_HOURS=20ч). К вечеру большинство честно expired; восемь подряд — и гвард решает, что API отдаёт заглушку:

status = "unknown" if info is None else _apply_stub_guard(api_info_to_status(info))
# срабатывание -> глобально, на все потоки, до первого настоящего active/soon

predictive.py уже решает ровно эту проблему через feed_stub_guard=False («серия expired подряд для сканера — норма»). /active имеет ту же природу, но опции не получил.

ИсправлениеНе кормить гвард из classify_wheels — счётчик должен видеть только поток свежих находок (parser, twitch-worker).
04

Гонка кулдауна между parser / twitch-worker / predictive

parser.py:754 · twitch.py:156 · predictive.py:205 проверено чтением кода

Проверка и установка кулдауна — две операции, между ними стоит сеть:

if cooldown_active(url, now): continue
status, ... = precheck_wheel(url, ...)   # ← 1–74 с сети
mark_url_alert(url, now)                 # ← метка только здесь

У parser окно ещё шире: метка ставится только после send_telegram_notification. Штатный сценарий: стример постит ссылку в Telegram-канал и в свой Twitch-чат одновременно — оба потока видят «кулдауна нет» и оба шлют.

ИсправлениеАтомарный claim_url_alert(url, now) в alerts.py — проверка и установка под одним локом, вызывать до precheck во всех трёх местах.
05

Анти-бан сканера не работает для 429

predictive.py:186 проверено чтением кода

probe_slug проверяет status_code in (403, 429), но 429 входит в status_forcelist общей сессии — urllib3 ретраит его 4 раза, бросает MaxRetryError, requests превращает в RetryError:

except requests.RequestException as error:
    return ERROR, "", False, ""   # ← 429 попадает сюда, не в BLOCKED

_notify_blocked() не срабатывает, PREDICTIVE_BLOCK_COOLDOWN_MINUTES не применяется — сканер делает 5 запросов на слаг именно тогда, когда его уже тормозят. Ровно риск из докстроки модуля: «бан по IP убьёт весь парсер».

ИсправлениеУбрать 429 из status_forcelist сессии сканера (или отдельная сессия без status-ретраев).

Подменная ссылка в уведомлении по ключевым словам

parser.py:110 · telegram_api.py:223 проверено чтением кода

Превью кладёт тег со сторонним href и независимой подписью, и он вставляется сырым в сообщение с parse_mode="HTML":

f'<a href="{html.escape(href, quote=True)}">{html.escape(label)}</a>'

Пробоя тега нет, но href и текст ссылки полностью контролирует автор поста. find_disallowed_domains не спасает: t.me, vk.com, twitch.tv в allowlist. Админ получает от собственного доверенного бота сообщение, где видимый текст — адрес колеса, а переход ведёт на чужого бота.

ИсправлениеРендерить "{label} ({href})" текстом, либо оставлять <a> только когда хост после normalize_url == betboom.ru.
07

Тесты зависят от .env разработчика

tests/conftest.py:15 проверено запуском

conftest подменяет только WHEELSPARSER_DATA_DIR. Собственный прогон:

$ PRECHECK_WHEELS=false pytest -q tests/test_parser.py
8 failed  (test_expired_wheel_is_not_notified, ...)

В CI зелено, у разработчика с локальным .env — красные тесты и час на выяснение, что код ни при чём. Хуже: заданные в .env TELEGRAM_BOT_TOKEN/TELEGRAM_CHAT_ID делают notifications_enabled() истинным в тестовом процессе — защита от отправки в реальный чат держится только на полноте моков.

ИсправлениеВ conftest.py жёстко задать TELEGRAM_BOT_TOKEN="", TELEGRAM_CHAT_ID="", PRECHECK_WHEELS=true, REALERT_COOLDOWN_MINUTES=30, USE_COLORS=false.

Сетевые вызовы под локами реестра

bot.py:632 и ещё ~9 мест проверено чтением кода 
with registry.CHANNELS_LOCK:
    if channel in registry.CHANNELS:
        bot_send(chat_id, "уже в списке", ...)   # ← POST под локом
        return

До ~74с удержания CHANNELS_LOCK блокируют process_cycle, save_seen. Для KEYWORDS_LOCK хуже — его берёт find_keywords на каждое сообщение цикла. В bot.py:604 автор сам пишет «сетевой запрос выполняем БЕЗ CHANNELS_LOCK» — правило есть, но в ранних ветках тех же функций нарушено.

ИсправлениеСобирать текст под локом, отправлять после выхода из with.

Лок /active отпускается до отправки результата

active_report.py:175 проверено чтением кода

_active_check_lock.release() стоит в finally вокруг classify_wheels, а background_bot_send идёт после. Поток A висит в отправке, второй /active запускает поток B — и оба работают с одной ACTIVE_CHECK_SESSION, у которой один заявленный владелец.

ИсправлениеПеренести release() в конец _run_and_send, после background_bot_send.
10

Утечка сокета при сбое TLS/JOIN

twitch.py:302 проверено чтением кода

Если wrap_socket или sendall бросят исключение, локальные raw_socket/sock теряются, а у вызывающего sock остаётся None — finally ничего не закрывает. При устойчивом сбое цикл переподключения (backoff 5→120с) повторяет это бесконечно.

ИсправлениеОбернуть создание сокета и NICK/JOIN в try/except BaseException: sock.close(); raise.
11

Остановка не прерывает опрос каналов

parser.py:257 проверено чтением кода

fetch() не смотрит на STOP_EVENT, а ThreadPoolExecutor.__exit__ делает shutdown(wait=True), который его тоже игнорирует. Ctrl+C посреди опроса каналов — цикл дочитывает все, join(timeout=20) истекает, save_seen пропускается.

ИсправлениеВ начале fetch(): if STOP_EVENT.is_set(): return channel, None.

streamers.json растёт бесконечно, наполняется из постов

predictive.py:332 проверено чтением кода

Ни merge_frontiers, ни scan_once не удаляют префиксы. Наполняется файл из frontier_from_history — по любой записи в базе, включая выдуманный слаг: несуществующий адрес → unknown → fail-open → уведомление → INSERT → новая «серия» навсегда. Проверено и снято

Гипотезы, которые не подтвердились при проверке — чтобы не тратить на них время повторно.

  • SQL-инъекцииВсе запросы в db.py параметризованы через `?`.
  • SSRF в resolve_shortlinkКаждый хоп перепроверяет хост; `vk.cc@127.0.0.1` не проходит.
  • Обход FREESTREAM_RE`evil.com@betboom.ru` не матчится, только буквальный домен.
  • Catastrophic backtrackingВсе regex линейны, без вложенных квантификаторов.
  • Path traversalИмена каналов/слагов нигде не используются как компонент пути.
  • Экранирование в командах ботаhtml.escape перед parse_mode=HTML — везде, кроме находки №6.
  • Подделка ролей в TwitchБейджи ставит сам Twitch поверх TLS, зритель их не контролирует.
  • Циклы в импортахГраф по AST циклов не показал, слои соблюдены.
  • Итерация по мутируемым словарямВезде материализован список внутри лока перед pop.
  • Дедлоки по порядку захватаНе найдены; вложенных чужих локов нет.
