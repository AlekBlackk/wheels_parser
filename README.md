# WheelsParser

Отслеживает публичные Telegram-каналы (через `t.me/s/<channel>`, без Telegram API) и Twitch-чаты (анонимный IRC, без токенов и OAuth), находит ссылки `betboom.ru/freestream/...` и присылает их в Telegram. В Telegram ищутся ссылки и ключевые слова, в Twitch — только ссылки от стримера, модераторов, VIP и известных ботов.

Перед отправкой статус колеса проверяется через API BetBoom (`PRECHECK_WHEELS`): уведомление уходит только по подтверждённому `active`, всё остальное молчит. Ссылка при этом не теряется — она ждёт в очереди перепроверки и уведомление придёт, как только колесо запустится. Находки хранятся локально, бот отвечает на команды.

## Запуск

Windows: установите Python 3.10+, скопируйте `env.example` в `.env`, заполните `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`, запустите `run.bat` — он сам создаст окружение и поставит зависимости.

Вручную:

```bash
python -m pip install -e .
python -m wheelsparser
```

Тесты — `python -m pytest`.

## Команды бота

Принимаются только из чата `TELEGRAM_CHAT_ID`.

| Команда | Действие |
|---|---|
| `/start` | Приветствие и краткая информация о боте |
| `/menu` | Меню управления кнопками (та же функциональность, что текстовые команды) |
| `/active` | Внеплановый обход всех каналов + живые колёса за сегодня (сброс в 00:00 МСК) |

| `/status` | Статистика найденных ссылок |

| `/help` | Список команд и текущие настройки |

## Файлы

Правятся руками: `.env` (создайте сами), `channels.txt`, `twitch_channels.txt`, `keywords.txt` — списки-источники правды, создаются автоматически при первом запуске и меняются командами бота.

Машинное состояние — в `data/` (переопределяется `WHEELSPARSER_DATA_DIR`, при апгрейде переносится из корня само): `wheels.db` (история находок, SQLite), `seen_ids.json` (обработанные сообщения), `bot_state.json` (offset бота — команды не выполняются повторно после рестарта), `removed_wheels.json` (скрытые из `/active`), `pending_expired.json` (ссылки, по которым `active` не подтвердился, и они ждут перепроверки — переживает рестарт, иначе такая находка терялась бы навсегда), `suggested_channels.json` (каналы-первоисточники, которые уже предлагали добавить — одно предложение на канал за всю историю), `streamers.json` (рубеж перебора слагов: до какого адреса каждая серия проверена и какие адреса ждут старта), `retired_streamers.json` (серии в отставке и дата отставки — она истекает через `PREDICTIVE_RETIRE_DAYS`), `watched_wheels.json` (последний известный `action_uid` по каждому наблюдаемому адресу — по его смене наблюдатель и узнаёт о перезапуске), `parser.log` (с ротацией, токен бота маскируется).

Запись истории: URL, время обнаружения, канал и источник (`telegram`/`twitch`/`predictive`), ID и URL сообщения, фрагмент текста, статус колеса, результат отправки.

**История в SQLite.** До версии 3.x история лежала в `freebets.json`: файл целиком переписывался в конце каждого цикла с находкой и целиком перечитывался на каждую команду бота. Теперь новая находка — это один `INSERT`, а `/status`, `/wheels`, `/active` и `/top` — запросы с `WHERE` и `GROUP BY` по индексам. Ставить ничего не нужно: `sqlite3` входит в стандартную библиотеку Python. При первом запуске новой версии `freebets.json` переносится в `wheels.db` автоматически и переименовывается в `freebets.json.migrated` — повторный импорт не выполняется. Режим WAL: чтения бота не блокируют запись парсера.

## Как это работает

**Время.** Все даты и счётчики — по Москве (UTC+3, без летнего времени), независимо от таймзоны сервера: `found_at`, `/status`, окно `/wheels`, суточный сброс `/active` в 00:00 МСК.

**URL.** Единая каноническая форма везде (извлечение, дедупликация, `/active`, кэши): без query-параметров и завершающего `/`, домен в нижнем регистре без `www`. Разные хвосты одной ссылки схлопываются в одну запись. Схема (`https://`) необязательна на входе: Twitch-боты (nightbot, StreamElements и т.п.) нередко режут её в сообщениях чата — такая ссылка находится и достраивается до `https://`, чтобы совпасть с тем же колесом из Telegram.

**Сокращатели.** Колесо, спрятанное за `vk.cc`, `clck.ru`, `bit.ly` или `tinyurl.com`, раньше не находилось вообще: регэксп видит только прямую ссылку на `betboom.ru`. Такие ссылки раскрываются одним-двумя редиректами (`HEAD` с фолбэком на `GET`, `SHORTENER_RESOLVE_TIMEOUT`) и дальше идут обычным путём. Результат кэшируется на `SHORTENER_CACHE_TTL_SECONDS`: канал перечитывает последние сообщения каждый цикл, и без кэша один и тот же адрес резолвился бы заново каждую минуту. В Twitch раскрытие делается только для сообщений от стримера, модов, VIP и ботов — оно стоит сетевого запроса. Сокращатель в белый список доменов для алертов по ключевым словам не добавлен намеренно: за ним прячется и скам-казино, поэтому проверяется уже раскрытый домен, а нераскрытый сокращатель остаётся подозрительным.

**Дедупликация.** Повтор того же URL подавляется на `REALERT_COOLDOWN_MINUTES`, потом уведомление уходит снова: колёса живут на постоянных адресах, и тот же URL может означать новый запуск. Кулдаун общий для Telegram и Twitch — дубль из двух источников не рассылается.

**Обновление по `/active`.** Команда не просто перечитывает базу: она сначала будит поток парсера на внеочередной обход всех Telegram-каналов (тот же `process_cycle`, что и по расписанию), ждёт его завершения — до `RESCAN_WAIT_TIMEOUT` секунд, иначе отчёт уходит по текущей базе с пометкой в `parser.log` — и только потом проверяет колёса через API BetBoom. Поэтому свежее колесо, опубликованное только что, попадает в ответ сразу, не дожидаясь очередного `CHECK_INTERVAL`. Twitch (живой IRC) и перебор слагов на `/active` не запускаются — они и так работают в реальном времени.

**Проверка статуса.** `betboom.py` спрашивает у API BetBoom не «что там по этому адресу», а конкретное действие: тело запроса — `{"action_uid": ...}`, подпись — в заголовке `x-action-signature`. Оба значения лежат в `__NEXT_DATA__` самой страницы колеса (`props.pageProps.uid` и `.hash`), поэтому одна проверка — это два запроса: страница и API. Подпись действительна сутки, а `action_uid` у колеса постоянен, поэтому пара кэшируется на `ACTION_SIGNATURE_TTL_SECONDS` и проверка снова стоит одного запроса. Прежний контракт (`{"streamer_link": ...}` без подписи) API не отвергает, а отвечает заглушкой — одинаковой на любой адрес, с `is_ended: true`. Заглушка опознаётся по форме ответа: если в `info` нет ни `action_uid`, ни `action_id`, статус — `unknown`, а не `expired`, иначе живые колёса молча считались бы завершившимися. Живой прогон 2026-09-06 показал, что в проде заглушки нет: подписанный запрос отдаёт настоящие данные по каждому колесу, а заглушка приходит только на неверный контракт (без подписи, с чужой подписью, старый `{streamer_link}`).

Сама страница колеса источником статуса быть не может: в `props.pageProps` всего 7 ключей (`uid`, `hash`, `staticUrl`, `hostUrl`, `seo_text` и константы SSR-заглушки seo-блока `code: 404` / `status: "NOT_FOUND"`, одинаковые у живого и у завершённого колеса). Единственное, что страница говорит о колесе сама, — HTTP 404: слага не существует (опечатка, обрезанная ссылка, удалённое колесо), это статус `missing` (исключение `betboom.WheelPageMissing`).

**Что отправляется.** Уведомление уходит только при явном `active`. Раньше действовал чёрный список — не слали `expired` и `soon`, а всё прочее, в первую очередь `unknown`, уходило в Telegram по принципу fail-open «лучше лишнее уведомление, чем пропущенное колесо»; именно это давало поток уведомлений о неактивных колёсах. Теперь `unknown` означает молчание, и fail-open в основном пути обнаружения нет. Ссылка при этом не теряется: она попадает в очередь перепроверки (см. «Доставка»), и уведомление придёт само, как только колесо действительно запустится. В очередь идёт и `missing` (страница отдала 404): чаще всего это выдуманный слаг, но тот же ответ приходит при блокировке и сбое CDN, а цена ошибки несимметрична — лишний дешёвый GET против потерянного живого колеса. Мусорные адреса уходят из очереди сами по истечении окна. Белый список `active` и раньше действовал в переборе слагов и в ретрае — теперь весь проект единообразен.

**Стоп-гвард.** Гвард чисто наблюдательный: статус он не подменяет, только пишет в `parser.log`, сервисного уведомления в Telegram по нему намеренно нет — слишком шумно. Счётчика два, потому что сбоя два, и признаки у них разные. Первый: `BETBOOM_STUB_GUARD_THRESHOLD` подряд идущих `unknown` — проверка перестала давать результат (заглушка без `action_uid`, протухшая подпись, блокировка); сбрасывается любым определённым статусом. Второй: `BETBOOM_STUB_GUARD_THRESHOLD × 5` проверок подряд без единого `active`/`soon` — подозрение на заглушку, которую по форме ответа не отличить (она выглядит как бесконечная серия честных `expired`); сбрасывается только настоящим живым колесом. Порог у второго выше, потому что серия `expired` бывает и в норме — ночью, к концу дня; цена ложной тревоги теперь одна строка в логе, а не рассылка. Раньше гвард считал подряд идущие `expired` и переводил их в `unknown` (fail-open), но серия `expired` — штатное состояние, а не признак сбоя: в `parser.log` их 84 против 36 `active`, и старый гвард исправно превращал завершившиеся колёса в рассылку. Повторные проверки одного и того же адреса счётчик не двигают.

**Expired-кэш.** Ссылка, признанная завершившейся (`expired`), на `EXPIRED_CACHE_TTL_SECONDS` кэшируется отдельно от `REALERT_COOLDOWN_MINUTES` — короткий TTL нужен только чтобы не бить по API BetBoom за один и тот же «хвост» в нескольких постах подряд, а не для подавления повторов (кулдаун на `expired` не ставится специально). Перепроверка ранее пропущенных ссылок (см. «Доставка» ниже) всегда обходит этот кэш.

**Доставка.** Пост разбирается по хэшу содержимого один раз, поэтому неудачная отправка (`notified: false`) повторяется в начале следующих циклов, пока не дойдёт (`NOTIFY_RETRY_WINDOW_MINUTES`, `NOTIFY_RETRY_MAX_PER_CYCLE`); переживает рестарт. Ретраятся обе находки: ссылки на колёса и посты с ключевыми словами (последние лежат в истории без поля `url` и в `/wheels`, `/status`, `/active` не показываются). Записи с неизвестным статусом доставки не повторяются — `sendMessage` не идемпотентен. Кандидаты на повтор сортируются не только по времени находки, но и по числу уже сделанных попыток: без этого запись, которая не доставляется раз за разом, как самая старая монополизировала бы весь `NOTIFY_RETRY_MAX_PER_CYCLE` каждый цикл, и более свежие находки не получили бы ни одной попытки до истечения окна. Ссылка, по которой уведомление не ушло, тоже не теряется навсегда: пост уже помечен «увиденным», и правка поста её не перепроверит, поэтому всё, что на момент находки не оказалось `active` (`expired`, `soon`, `unknown`), кладётся в очередь перепроверки (`retry_expired_links`) и проверяется каждый цикл мимо кэша в течение `NOTIFY_RETRY_WINDOW_MINUTES` — как только колесо запустится (или выяснится ошибка API либо неточный расчёт дедлайна), уведомление уйдёт задним числом. Оповещение и здесь идёт только по подтверждённому `active`: `unknown` — это «проверить не удалось», а не «ожило», и рассылка по нему превратила бы весь накопленный список в пачку устаревших уведомлений. `missing` (страница отдала 404) попадает в очередь наравне с остальными: 404 бывает и у живого колеса при блокировке или сбое CDN. Список ждущих перепроверки переживает рестарт (`pending_expired.json`): пост уже помечен «увиденным», и без файла рестарт терял бы такие находки навсегда.

**Дедлайн.** Конец розыгрыша считается сам (`start_dttm` + `duration_min` из API BetBoom, флаг `is_ended` запаздывает) и показывается в уведомлении и `/active`: «до 21:40 (осталось 12 мин)». Остаток пересчитывается в момент отправки, поэтому верен и в повторной попытке. Срок неизвестен (сбой API или колесо без времени старта) — строка не показывается.

**Перебор слагов.** Адреса колёс у стримера идут серией: `zonertg4`, `zonertg5`, … / `LOLLY08`, `LOLLY09`, … Разведка по betboom.ru показала, что страница колеса существует ещё до того, как стример выложит ссылку (создано, но не запущено — статус `soon`), несуществующий слаг честно отдаёт 404, а регистр значим: `LOLLY08` отдаёт 200, `lolly08` — 404. Поэтому следующие адреса серии проверяются заранее, и колесо находится без всякого поста. Ценность не только в упреждении: на момент разведки у серии `zonertg` существовали адреса 4…11, а в базе находок было три из них — перебор находит и уже идущие колёса, которые иначе пропущены совсем.

Серии не задаются руками: рубеж берётся из истории находок (что уже нашли Telegram и Twitch) плюс из `streamers.json`, так что новый стример подхватывается сам, как только его первое колесо найдено обычным путём. Ширина числа сохраняется — `LOLLY09`, а не `LOLLY9`. Уведомление уходит только по подтверждённому `active` — как и во всём остальном проекте: 404 даёт `missing`, сбой проверки — `unknown`, а рассылать по угаданному адресу, о котором API ничего не сказал, нельзя. Найденное завершившимся колесо молча двигает рубеж — уведомлять о прошедшем незачем. Созданное, но не запущенное запоминается в `pending` и перепроверяется каждый проход, пока не стартует; ожидающих в серии может быть несколько сразу.

Перебор идёт по чужому адресному пространству, а бан по IP убил бы весь парсер, поэтому осторожность встроена: пауза между запросами, остановка на первом 404 (реальные серии сплошные), суточный потолок запросов, и немедленное молчание с уведомлением админу при 403/429. Находки перебора исключены из счётчика стоп-гварда (`BETBOOM_STUB_GUARD_THRESHOLD`): сканер намеренно ходит по несуществующим и старым адресам, и серия неопределённых ответов подряд для него — норма, а не признак сбоя.

Слаг без числового хвоста (`jester`, `nix`, `bolt`) — это база серии, `(префикс, 0, 0)`: такой стример тоже заводит серию, и следующие адреса (`nix1`, `bolt1`) проверяются наравне с остальными. Раньше половина найденных слагов серию не заводила вовсе. Голый адрес серии существует и переиспользуется сам по себе (`zonertg` при известных `zonertg3…13`, `over`, `LOLLY`) — его проверяет наблюдатель, см. ниже. Отставка серии после `PREDICTIVE_MAX_EMPTY_SCANS` пустых проходов теперь временная (`PREDICTIVE_RETIRE_DAYS`): бессрочная означала, что стример, притихший на неделю, выпадает из перебора навсегда.

**Перезапуск на известном адресе.** Перебор отвечает на вопрос «какой адрес появится следующим», и это меньшая часть работы: на проде из 816 колесо-дней за 58 суток 595 (73%) пришлись на адрес, который уже был в истории, и только 221 — на адрес, увиденный впервые. Слаг у стримера постоянный (`aunkereref` отстрелял 29 разных дней, `MAGER01` — 26), а розыгрыш на нём запускается заново, и узнать об этом перебором нельзя в принципе.

Поэтому рядом работает наблюдатель (`rearm.py`): он обходит уже известные адреса и ловит момент, когда на адресе стартовал новый розыгрыш. Детектор дешёвый — страница колеса отдаёт `props.pageProps.uid`, постоянный идентификатор действия; пока uid тот же, на адресе ничего не изменилось. Сменился — значит это другое действие, и только тогда идёт запрос к API за статусом. Один запрос на адрес вместо трёх. Уведомление, как и везде, уходит только по подтверждённому `active`; адрес, увиденный впервые, молча запоминается — сравнивать не с чем, и первый проход не должен рассылать всю историю разом.

Каждый проход заканчивается строкой в `parser.log`: `Наблюдатель: проверено 62 из 120 · живых 60 · перезапусков 0 · бюджет 62/3000`. Она пишется всегда, даже когда находок нет: сам по себе наблюдатель молчалив, и без этой строки его работа видна только по времени изменения `watched_wheels.json` — то есть молчание неотличимо от «модуль выключен» и от «поток упал».

Список адресов не ведётся руками: он берётся из истории находок за `REARM_WINDOW_DAYS` и сортируется по «горячести» — числу разных дней, в которые адрес отметился (по числу записей одно болтливое колесо вытеснило бы всех остальных). К нему добавляются голые адреса серий. Обход идёт по кругу: каждый проход берёт столько адресов, сколько разрешил планировщик, и следующий продолжает с того же места.

**Бюджет по времени суток.** Суточный потолок `PREDICTIVE_DAILY_BUDGET` общий для перебора и наблюдателя, и тратится он не подряд, а пропорционально весу часа: 14:00–21:00 МСК дают 71% находок, 10:00–13:00 и 22:00 — ещё 24%, на остальные одиннадцать часов приходится меньше 5%. Прежний сканер тратил бюджет подряд от полуночи и замолкал днём — то есть был слеп ровно в те часы, когда колёса и запускают. Ночью проход всё равно получает хотя бы один запрос: ночные запуски редки, но полная слепота означала бы, что их не увидит никто. Внутри прохода приоритет у наблюдателя — он покрывает большую долю находок, остаток достаётся разведке вперёд; блокировка у любого из двух останавливает весь проход, потому что 403/429 адресован нашему IP, а не механизму.

**Первоисточники репостов.** Если пост с колесом (или с ключевым словом) оказался репостом из канала, которого нет в мониторинге, бот присылает служебное сообщение с кнопкой «➕ Добавить» — добавление проходит ту же проверку ленты `t.me/s`, что и `/add`, а юзернейм из кнопки валидируется заново. Предложение не зависит от того, ушло ли уведомление о самом колесе: чаще всего репост несёт ссылку, о которой уже оповестили из другого канала, — находки нет, а первоисточник как раз есть. Одно предложение на канал за всю историю (`suggested_channels.json`): молчание админа — тоже ответ. Репост из скрытого источника (закрытый канал) первоисточника не выдаёт — Telegram не отдаёт ссылку.

**Twitch.** Подключение анонимное (`irc.chat.twitch.tv:6697`, SSL, ник `justinfan*`). Ключевые слова в чатах не ищутся — зрители пишут «колесо» постоянно. Уведомление уходит сразу, не дожидаясь цикла Telegram; записи попадают в историю с `"source": "twitch"`. Работа разнесена на два потока: `twitch-irc` только читает сокет, `twitch-worker` ходит в API и шлёт уведомления — иначе HTTP-вызов блокирует чтение сокета, ответ на PING опаздывает и Twitch выбрасывает парсер из чата. `/addtwitch` и `/removetwitch` применяются на лету, без перезапуска. У IRC нет истории: сообщения за время простоя парсера не восстанавливаются. Ссылка, по которой не подтвердился `active` (`expired`, `soon`, `unknown`), ставится на ту же перепроверку, что и в Telegram: раньше она терялась навсегда — сообщение в чате не «правится», а зрители после анонса ссылку обычно не повторяют, поэтому колесо, начавшееся позже, оставалось без уведомления. Регистрацию делает поток парсера (заявка передаётся ему очередью): список ждущих перепроверки принадлежит только ему.

## Живучесть

Что процесс переживает без ручного вмешательства:

| Отказ | Реакция |
|---|---|
| Ошибка внутри цикла парсинга | цикл пропускается, следующий идёт по расписанию |
| Необработанная ошибка в потоке (`parser`, `bot`, `twitch-irc`, `twitch-worker`, `predictive`) | перезапуск потока (пауза 5 → 300 сек), одно уведомление на серию сбоев |
| betboom.ru ответил 403/429 на перебор слагов | перебор замолкает на `PREDICTIVE_BLOCK_COOLDOWN_MINUTES`, админу уходит уведомление |
| Обрыв или зависание Twitch IRC | переподключение с backoff 5–120 сек, вотчдог `TWITCH_IDLE_TIMEOUT_SECONDS` |
| API BetBoom отвечает заглушкой (в `info` нет `action_uid`/`action_id`) | статус `unknown`, уведомление не уходит, ссылка ждёт в очереди перепроверки (`NOTIFY_RETRY_WINDOW_MINUTES`) |
| Проверка статуса перестала давать результат вовсе | после `BETBOOM_STUB_GUARD_THRESHOLD` подряд `unknown` — предупреждение в `parser.log`; счётчик сбрасывается любым определённым статусом |
| Страница колеса отдала 404 | статус `missing`, уведомления нет, ссылка ждёт в очереди перепроверки — 404 бывает и временным |
| API отдаёт правдоподобную заглушку (всё выглядит как `expired`) | после `BETBOOM_STUB_GUARD_THRESHOLD × 5` проверок подряд без единого `active`/`soon` — предупреждение в `parser.log`: по форме ответа такую заглушку не отличить, и парсер молчал бы зря |
| Канал недоступен (404, сеть) | уведомление после `CHANNEL_FAIL_THRESHOLD` циклов |
| Канал открывается, но постов нет | уведомление после `CHANNEL_EMPTY_THRESHOLD` циклов |
| Постов нет разом во всех каналах | одно уведомление «похоже, изменилась вёрстка t.me/s» — иначе отказ невидим: каналы считались бы исправными |
| Второй запущенный экземпляр | не стартует, блокировка lock-файла |

## Структура кода

| Слой | Модули |
|---|---|
| Инфраструктура | `config.py` (настройки, регэкспы, значки), `logging_setup.py`, `timeutils.py` (МСК), `net.py` (HTTP-сессии, по одной на поток), `runtime.py` (`STOP_EVENT`, сигналы, супервизор потоков, lock) |
| Данные | `registry.py` (списки каналов и слов), `storage.py` (JSON-состояние), `urls.py` (канонизация, хэш поста), `keywords.py`, `alerts.py` (кулдаун) |
| Внешние API | `betboom.py` (статус колёс, кэш завершившихся), `telegram_api.py` (отправка) |
| Логика | `parser.py` (обход Telegram, контроль отказов каналов), `twitch.py` (IRC + обработчик), `predictive.py` (перебор слагов), `bot.py` (команды, `getUpdates`), `active_report.py` (`/active`) |
| Запуск | `app.py` — `main()`, потоки под супервизором |

Зависимости направлены сверху вниз, циклов нет. Подробности — в докстрингах модулей.
